## The one thing to do first (2 minutes)

The judge deployment (`gpt-5.4-mini-1`, westus3, sku DataZoneStandard) is provisioned at capacity 150,
which is 150K tokens per minute and 150 requests per minute. One judge call sends the whole transcript,
about 95K tokens at the median and up to 160K. Two consequences:

- any transcript above ~150K tokens can never be judged (the 37 old unjudged rows are all 148K-160K);
- when 60 rollouts finish within a few minutes, most judge calls exhaust their 10-minute retry window
  and the row is stored with `judge = null`. The guardian's rejudge pass then re-labels them at about
  1.5 rows per minute, so the morning tables may lag the rollout counts.

Raising the capacity is pay-per-token (no standing cost), reversible, and the region has 10,000K TPM of
headroom for this SKU. I tried to apply it and the action was blocked by the permission classifier, so I
did not retry. If you want it, this is the command (the model version is whatever the deployment has now):

```
az cognitiveservices account deployment create --name yilongjack2001-6481-resource --resource-group IncidentFox \
  --deployment-name gpt-5.4-mini-1 --model-name gpt-5.4-mini --model-format OpenAI \
  --model-version "$(az cognitiveservices account deployment show --name yilongjack2001-6481-resource \
      --resource-group IncidentFox --deployment-name gpt-5.4-mini-1 --query properties.model.version -o tsv)" \
  --sku-name DataZoneStandard --sku-capacity 2000
```

After that, `python scripts/rejudge_phase.py prompt_sweep_vllm signed_pack prompt_channel` on the box

## What broke and what I changed (all committed)

1. **Round-robin over the three vLLM servers collapsed onto one server** (16 running / 40 waiting vs 2 / 2):
   a rollout is a serial chain of requests, so once one server queues, chains stall there while the other
   servers keep re-dispatching into it. Replaced by least-in-flight dispatch. Sweeps restarted at 06:29 UTC;
   the 20 minutes of in-flight rollouts before that were lost. Servers now balanced at 15-16 running each,
   generation throughput 400-530 tok/s per server (was 75 on the overloaded one).
2. **dp_plant_geometry.py OOMed** because it shared GPU 5 with an HF worker (59 GB). Added a
   `/mnt/scfx_logs/reserved_gpus` file the guardian honours, reserved GPU 5, and ran the layer-wise version
   (`dp_plant_layers.py`, which subsumes the L19-only script and adds the prompt-end measurement). GPU 5
   returns to the HF pool automatically when the job exits.
3. **Judge quota** as above. rejudge_phase.py now takes the newest rows first and compacts only transcripts
   that exceed the quota (assistant turns keep their tail, tool outputs shortened); the sidecar records
   `compacted` so the analyses can count such labels. Analyses merge `rejudge.jsonl`.
4. **Throughput collapse from KV-cache thrash.** Every rollout runs to the 80-turn cap and contexts reach 75k
   tokens; at 20 rollouts per server the 1.57M-token KV cache was oversubscribed, preemptions started and
   each turn took ~4 minutes (233 s latency per request), so a rollout would take ~5 hours against ~20 minutes
   in the earlier run. At 07:17 UTC I retired the two random-direction workers (GPUs 3, 6) and one of the three
   completion_drive workers (GPU 7), started vLLM servers there, and restarted the sweeps at 10 rollouts per
   server across six servers (pd 50 + pt 10). Cost: the in-flight rollouts of the 06:29 restart (about 48 minutes
   of progress) and the three HF rollouts in progress. Expected: ~130 rollouts per hour, N=60 for all seven
   variants in roughly 3.5 hours. Swap completed 07:19:33 UTC; the swap's kill pattern also matched the
   rejudge process (its arguments name the sweep phase), so the guardian relaunched that pass at its next tick.
5. `pkill -f` from an ssh one-liner killed the one-liner's own shell (and the guardian). Guardian is now
   started through `infra/ensure_guardian.sh`. I also mistakenly killed a freshly relaunched rejudge process
   once (4 s old); the guardian relaunches it, cost about 5 minutes.
